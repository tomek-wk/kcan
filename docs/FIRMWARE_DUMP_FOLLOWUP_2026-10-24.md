# Dalsze poszukiwania firmware MCU i aktualizatorów — Commander 1.4–6.0 oraz pokrewne (2026-10-24)

**Metoda:** wyszukiwanie wielojęzyczne RU/PL/EN/FR, bez uruchamiania niezaufanych aplikacji ani programowania adaptera; dostęp do nazwanych załączników sprawdzano przez strony źródłowe i akcje pobierania w przeglądarce. Zbadano również **rzeczywistą zawartość tekstowego Intel HEX odczytanego przez publiczne API GitHub**, co nie oznacza pobrania archiwum Commandera. Sieciowe pobieranie do lokalnego kontenera jest w tym środowisku zablokowane DNS; odczyt źródeł GitHub przez połączone narzędzie działa. Opis „brak dostępu” dotyczy tylko konkretnej próby, nie dowodzi, że archiwum zostało usunięte.

**Dokument kontynuuje** [FIRMWARE_DUMP_LEADS_2026-10-23.md](FIRMWARE_DUMP_LEADS_2026-10-23.md) (FD-001–FD-014). Nie powiela niezweryfikowanych twierdzeń o oryginalności; nie umieszcza obcego firmware w repo.

## Zweryfikowana statycznie zawartość dostępnych plików HEX (FD-021)

Poniższe pliki zostały **faktycznie odczytane jako tekst z publicznego GitHub** i przeprowadzone przez ręczny parser Intel HEX w JS (żaden kod z plików nie był wykonywany). Sprawdzono liczbę rekordów, zgodność długości z rekordem, arytmetyczną kontrolę sum każdej linii oraz zakres adresów. Rekord typu 04 `Extended Linear Address` został uwzględniony.

| Ścieżka | Wiersze | Rekordy danych / EOF / Extended Linear Address | Bajty danych | Adres min-max | Błędne rekordy / sumy |
| --- | ---: | --- | ---: | --- | ---: |
| `test/app.hex` | **32** | **30 / 1 / 1** | **448 B** | **0x000800 – 0xF0000F** | **0** |
| `test/test1.hex` | **9** | **8 / 1 / 0** | **126 B** | **0x001038 – 0x001375** | **0** |
| `test/test2.hex` | **10** | **9 / 1 / 0** | **144 B** | **0x001030 – 0x00136F** | **0** |

`app.hex` jest **rzadką mapą rekordów HEX**, a nie ciągłym, 15 MB obrazem binarnym: wysoki adres dotyczy innego regionu pamięci PIC (np. EEPROM w HEX), a **suma bajtów faktycznie opisanych danymi to tylko 448**. Plik jest przykładem *aplikacji testowej* współpracującej z `mpcanflash`; **nie może być uznany za odczyt oryginalnej pamięci programu VAG K+CAN ani za implementację jego protokołu**. W żadnym z tych dostępnych przykładów nie potwierdzono dekodera UART `0x53/0x70`.

## Co blokuje inspekcję rzeczywistych firmware Commandera?

1. **CXEM:** widoczne oryginalne odnośniki do `CAN-PIC18F25K80.RAR`, `PIC18F2480.ZIP`, `PIC18F25K80.RAR`, `KCAN-ELM327.RAR`. Klikanie kończy się błędem pobrania / we wcześniejszych próbach 403. **Nie sprawdzono bajtów ani hashy**.
2. **Carmasters:** `PIC18F248.rar` i archiwum z przeróbką ELM opisano w poście. Archiwum nie zostało pobrane; strona/załączniki mogą wymagać konta.
3. **SuperVAG:** linki `resettools.com/app/supervag_k_can/updaterX.zip` prowadzą do niedostępnej domeny albo timeoutu. Nie jest pewne, że komercyjne aktualizatory zawierają pliki bez szyfrowania.
4. **GitHub:** połączony dostęp do publicznych plików tekstowych działa; odczyt `.hex` zakończył się sukcesem, ale to **nie** dump Commandera. GitHub code search po `KCAN-ELM327`, `pic18f2480.hex`, `VAG CAN Commander firmware` nie wykazał zawartego w nim pewnego HEX z Commandera. Znalezione dwa popularne repozytoria `VAG-K-CAN-Commander` z identycznym README służą pobieraniu, nie publikują firmware.
5. **Ograniczenie lokalnego kontenera:** próba `requests.get` do stron CXEM i do `raw.githubusercontent.com` zwraca błąd DNS; dostęp przez narzędzie WWW i połączone GitHub to odrębne kanały o innych ograniczeniach.

## Wniosek i dalszy kierunek

**Rzeczywisty HEX odczytany: TAK**, ale **tylko cudzy, drobny przykład testowy z bootloadera PIC18FxxK80, NIE wsad Commandera**. **Autentyczny HEX PIC z K+CAN: 0 pozyskanych**. Nie utożsamiać serii SuperVAG z wersjami Commandera; nie interpretować niemożności pobrania jako braku archiwów. Własnego urządzenia nie dotykano.

**Priorytet:** przejąć legalnie załączniki FD-001/003/005/015 (w szczególności CXEM 2025) albo znaleźć publiczne mirrory plików; po pobraniu nie uruchamiać EXE, tylko zidentyfikować archiwum, rozpakować i odtworzyć algorytmy `0x53` i `0x70`. Firmware różnego PIC lub nawet z inną implementacją protokołu jest nadal cenny jako **źródło hipotez i kontrolowanych testów**, zgodnie z decyzją użytkownika.
